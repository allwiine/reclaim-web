# Repo CI Safety Net Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** No change reaches main (and production) without a passing `astro build` and clean html-validate; dependency updates arrive as PRs vetted by the same gate.

**Architecture:** One GitHub Actions workflow (`build-and-validate` job) runs on every PR and on pushes to main. html-validate is wired as a lockfile-pinned devDependency with an npm script so CI and local runs agree. A repository ruleset makes the check required on main. Dependabot files monthly update PRs that flow through the same gate.

**Tech Stack:** GitHub Actions, html-validate, Dependabot, `gh` CLI. Site is Astro 7, deployed by Cloudflare Workers Builds on push to main (deploys are OUT of scope — do not create a deploy workflow).

**Spec:** `docs/superpowers/specs/2026-08-17-repo-ci-design.md`

## Global Constraints

- Node floor comes from `package.json` `engines.node` (`>=22.12.0`); the workflow must read it via `node-version-file: package.json`, never hardcode a version.
- `astro` stays the only runtime dependency; `html-validate` is a devDependency only.
- The status-check context is exactly `build-and-validate` — the workflow job id and the ruleset context must match character-for-character.
- Conventional Commits; one logical change per commit; commit messages must NOT contain `Co-Authored-By`, "Generated with Claude Code", or any AI-attribution trailer (repo owner's global rule — overrides any default).
- Never bypass hooks (`--no-verify` forbidden). If a build/validate step fails, STOP and report the exact error to the developer; do not edit site HTML or relax validation rules to force a pass.
- Work happens on the existing `chore/repo-ci` branch (already created from origin/main; contains the spec commit).

### Task 1: html-validate wiring (born-green gate)

**Files:**
- Create: `.htmlvalidate.json`
- Modify: `package.json` (add devDependency + `validate` script)
- Modify: `package-lock.json` (via npm, do not hand-edit)

**Interfaces:**
- Produces: `npm run validate` — validates `dist/**/*.html`, exit 0 on clean. Task 2's workflow calls it verbatim. Assumes `npm run build` ran first.

- [ ] **Step 1: Install html-validate as a devDependency**

```bash
npm install --save-dev html-validate
```

Expected: `package.json` gains `"html-validate"` under `devDependencies`; `package-lock.json` updated. Run `npm ls html-validate` and confirm it prints one entry with no errors.

- [ ] **Step 2: Create the config**

Create `.htmlvalidate.json` with exactly:

```json
{
  "extends": ["html-validate:recommended"]
}
```

- [ ] **Step 3: Add the validate script**

In `package.json`, add to `"scripts"` after `"preview"`:

```json
"validate": "html-validate \"dist/**/*.html\""
```

(The quotes matter: the glob is passed to html-validate's own glob handling, not the shell's.)

- [ ] **Step 4: Run the check against a fresh build — verify it fails without dist, then passes with it**

```bash
rm -rf dist && npm run validate
```

Expected: non-zero exit (no files match — proves the script actually looks at dist). Then:

```bash
npm run build && npm run validate
```

Expected: build exits 0, validate exits 0 with no errors reported. If validate reports errors: STOP. Report the exact rule IDs, files, and line numbers to the developer and wait — do not change `.htmlvalidate.json` rules or site source to force green.

- [ ] **Step 5: Commit**

```bash
git add package.json package-lock.json .htmlvalidate.json
git commit -m "chore: wire html-validate with the recommended preset"
```

### Task 2: CI workflow

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: `npm run validate` from Task 1; `npm run build` (exists).
- Produces: a check run named `build-and-validate` on every PR and main push. Task 5's ruleset references this exact name.

- [ ] **Step 1: Verify the action major tags exist**

```bash
gh api repos/actions/checkout/git/ref/tags/v5 --jq .ref
gh api repos/actions/setup-node/git/ref/tags/v5 --jq .ref
```

Expected: `refs/tags/v5` for each. If a tag is missing, list tags with `gh api repos/actions/<name>/tags --jq '.[].name'` and use the highest major that exists, updating the workflow below to match.

- [ ] **Step 2: Create the workflow**

Create `.github/workflows/ci.yml` with exactly:

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-and-validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version-file: package.json
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm run validate
```

Do not add a `name:` to the job — the check-run name must stay the job id `build-and-validate`.

- [ ] **Step 3: Syntax-check the YAML**

```bash
npx --yes js-yaml .github/workflows/ci.yml > /dev/null && echo YAML-OK
```

Expected: `YAML-OK`.

- [ ] **Step 4: Commit**

```bash
git add .github/workflows/ci.yml
git commit -m "ci: build and html-validate every PR and push to main"
```

### Task 3: Dependabot

**Files:**
- Create: `.github/dependabot.yml`

**Interfaces:**
- Consumes: nothing. Produces monthly update PRs whose checks are Task 2's workflow.

- [ ] **Step 1: Create the config**

Create `.github/dependabot.yml` with exactly:

```yaml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: monthly
    groups:
      minor-and-patch:
        update-types:
          - minor
          - patch
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: monthly
```

- [ ] **Step 2: Syntax-check the YAML**

```bash
npx --yes js-yaml .github/dependabot.yml > /dev/null && echo YAML-OK
```

Expected: `YAML-OK`.

- [ ] **Step 3: Commit**

```bash
git add .github/dependabot.yml
git commit -m "ci: add monthly dependabot updates for npm and actions"
```

### Task 5: Branch-protection ruleset on main

**Files:** none (GitHub API state, no commit).

**Interfaces:**
- Consumes: the `build-and-validate` check context proven live in Task 4.
- Produces: ruleset `main-protection` on the default branch.

- [ ] **Step 1: Create the ruleset**

```bash
gh api repos/allwiine/reclaim-web/rulesets --method POST --input - <<'EOF'
{
  "name": "main-protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": {
      "include": ["~DEFAULT_BRANCH"],
      "exclude": []
    }
  },
  "rules": [
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [
          { "context": "build-and-validate" }
        ]
      }
    }
  ]
}
EOF
```

Expected: JSON response containing `"name": "main-protection"` and an `id`.

- [ ] **Step 2: Verify the ruleset is active**

```bash
gh api repos/allwiine/reclaim-web/rulesets --jq '.[] | {id, name, enforcement}'
```

Expected: one entry, `"name": "main-protection"`, `"enforcement": "active"`.

- [ ] **Step 3: Verify the PR now shows the required check satisfied**

```bash
gh pr view --json mergeStateStatus,statusCheckRollup \
  --jq '{merge: .mergeStateStatus, checks: [.statusCheckRollup[] | {name, status: (.conclusion // .status)}]}'
```

Expected: checks include `build-and-validate` with `SUCCESS`; `merge` is `CLEAN` (or `BLOCKED` only while a check is still running — re-run after it finishes). Do NOT test the ruleset by pushing to main directly; a misconfigured ruleset would let the push through and trigger a production deploy.
